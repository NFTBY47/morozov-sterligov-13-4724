# ЛР3. Ограничения размера пакета

Вариант: **Clearing**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/eligibility.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `ClearingService.add()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте `ClearingEligibilityRule` и два наследника.

`MaximumBatchCountRule(3)` проверяет `len(transactions) + 1 <= 3`; отказ — `BATCH_COUNT_LIMIT`. Настройка `maximum` должна быть целым числом не меньше `1`.

`MaximumBatchAmountRule(100 EUR)` проверяет `total + amount <= 100 EUR`; отказ — `BATCH_AMOUNT_LIMIT`. Нулевой максимум суммы допустим. Правила только проверяют возможность добавления, но не меняют пакет.

### Шаг 2. Соберите путь вызова в `ClearingService.add()`

Получите пакет, вызовите `validate_add(tx)` и готовую `ensure_unassigned()`, затем правила по порядку. Только после успеха вызовите `add_transaction(tx)` и верните снимок через `get_batch()`. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

После добавления T1 попытка T2 сверх суммы отклоняется; исправленная T2 добавляется. Прежний снимок пакета не меняется.

## Примеры и границы

- Третья операция допустима, четвёртая — нет.
- При сумме `90` добавление `10` допустимо, `10.01` — нет.
- Отказ не меняет сумму и число операций.
- Обязательные проверки добавления выполняются раньше дополнительных правил.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
